# 功能与代码规划

> 这份文档把产品能力映射到 Action ID、代码位置和验收方式。
> 任务的实际优先级与勾选状态以[开发计划](./开发计划.md)为准；
> 本文负责说明「为什么需要这组能力，以及代码应该落在哪里」。

## 1. 当前基线

当前已经注册 9 个业务 Action：

| 能力 | Action ID | 当前实现 |
|---|---|---|
| 文件结构化检查 | `document.inspect` | `crates/redline-core/src/inspect.rs` |
| 文件差异 | `document.diff` | `crates/redline-core/src/diff.rs` |
| docx 修订输出 | `document.apply-track-changes` | `crates/redline-core/src/apply.rs` |
| 可解析性验证 | `document.verify` | `crates/redline-core/src/lib.rs` |
| 格式能力表 | `document.formats` | `crates/redline-core/src/format.rs` |
| 压缩包列表 | `archive.list` | `crates/redline-core/src/archive.rs` |
| 压缩包解出 | `archive.extract` | `crates/redline-core/src/archive.rs` |
| Agent 清单 | `agent.catalog` | `crates/redline-core/src/agent.rs` |
| Agent 派发 | `agent.dispatch` | `crates/redline-core/src/agent.rs` |

调用面：

```text
GUI ─┐
CLI ─┼─→ redline_core::dispatch(action_id, params) → 统一信封
MCP ─┘                     （计划）
```

任何新增业务能力先加核心 Action 和测试，再给 GUI/CLI/MCP 加薄调用面。

## 2. 完整产品循环

```text
打开文件
  → 识别格式并预览
  → 标注区域和整体要求
  → 生成机器可读工单
  → 选择 Claude/Codex/本地/云 Agent
  → 写出新文件
  → 对照差异
  → 接受、继续向右，或回到旧版本分叉
```

对应数据对象：

- `DocumentSnapshot`：人和 Agent 对同一文件结构的共同视图；
- `Annotation`：分数坐标、unit、类型和说明；
- `WorkOrder`：源文件哈希、标注、整体要求、目标输出和权限；
- `VersionNode`：不可变文件快照及其元数据；
- `ActionEdge`：从父版本生成子版本的一次 Agent 动作；
- `DiffReport`：结构化差异和可视化定位。

## 3. 建议新增的核心 Action

Action 名在实现前需要补进[动作契约](./动作契约.md)，以下是规划草案。

### 3.1 工单

| Action | 作用 | 为什么不能只在 GUI 做 |
|---|---|---|
| `workorder.create` | 把源文件哈希、标注、整体要求和输出约束固化为工单 | CLI/MCP/GUI 必须给 Agent 同一份要求 |
| `workorder.verify` | 检查源文件是否陈旧、输出是否会覆盖、格式能力是否匹配 | 安全拒绝不能依赖某个界面 |
| `workorder.export` | 导出可移植 JSON/Markdown 工单 | 方便交给任何外部 Agent，不绑定官方云 |

`agent.dispatch` 应逐步改成消费 `WorkOrder`，不要继续拥有第二份工单拼装规则。

### 3.2 版本图

| Action | 作用 |
|---|---|
| `version.create` | 从文件内容和元数据创建不可变节点 |
| `version.list` | 列出某项目的节点与边 |
| `version.get` | 读取单个节点、产物和审计信息 |
| `version.branch` | 从任意旧节点发起新分支 |
| `version.adopt` | 用户明确确认后导出/替换工作文件，并先留底 |

节点内容建议按 sha256 寻址，元数据使用 SQLite；大文件不复制时可先硬链接/引用，
但必须检测原路径变化，不能把可变路径伪装成不可变节点。

### 3.3 系统集成

文件关联和右键菜单本身是安装器/宿主行为，不应伪装成跨平台业务 Action。
但可测试的注册计划可以抽成纯数据：

- 核心格式表给出建议关联和能力；
- 安装器根据用户勾选生成注册表操作；
- 安装前备份归属，卸载时只撤销自己创建的项；
- 端到端测试在干净 Windows 沙箱验证安装、打开、卸载和还原。

## 4. 格式能力规划

### Tier A：可靠主路径

目标：预览、结构抽取、差异定位和 Agent 工单都可靠。

- 文本/Markdown/代码、HTML；
- 常见图片；
- PDF；
- docx、xlsx；
- zip 及文件夹。

### Tier B：先看懂

目标：能预览或给出结构化大纲，修改主要交给外部 Agent/原软件。

- pptx；
- PSD；
- DXF；
- STL/OBJ/GLTF；
- rar/7z/tar/gz/xz/iso/cab。

### Tier C：外部转换

通过 LibreOffice、7z、OCRmyPDF 等进程外工具转换或补充能力。每个外部工具必须有：

- 明确来源、版本和许可证；
- 超时、取消、临时目录和残留清理；
- 输出再次经过叠象安全检查；
- 未安装时的可读错误和安装指引；
- 干净机测试。

### 下一批按真实需求排序

候选：eml/msg、sqlite、mp4/mp3、apk、字体、epub、heic、dwg 只读转换。
不要按开发者兴趣排；记录匿名扩展名失败计数和用户投票，按实际打不开次数推进。

## 5. 里程碑

### M0：成为真正的打开入口

对应开发计划 P0/P1。

- 文件关联、Open With、右键打开和解压；
- rar/7z 等常见压缩格式；
- 拖放文件和文件夹；
- 签名安装包、干净卸载、可回滚更新；
- 常见格式首屏性能和失败文案。

退出条件：在干净机上连续使用两周，用户可以忘记软件本身，只通过双击和右键完成工作。

### M1：成为 Agent 的文件工具层

对应 P2，并提前固化 WorkOrder。

- `redline-mcp`；
- `workorder.*`；
- Claude Code、Codex 各有官方配置与端到端用例；
- Agent 结果必须落到指定输出路径；
- 工单预览、权限披露、超时和取消。

退出条件：外部 Agent 不启动 GUI，也能 inspect、diff、生成工单和产出新文件。

### M2：无限修改模式

对应 P3。

- `version.*` 核心和 CLI；
- 不可变节点、父指针、分支和内容哈希；
- 画布平移/缩放，横向迭代、纵向分叉；
- AI 动作卡折叠、重放和换 Agent；
- 左右视觉差异与结构化差异联动。

退出条件：同一原件产生至少两层连续修改和两个平行分支，退出应用后完整恢复，
源文件哈希始终不变。

### M3：官方云服务

对应 P4。

- `AgentSpec` 支持本地进程和远程 HTTP；
- 同一 WorkOrder、同一输出约束；
- 估价、余额、用量、取消、退款和错误分类；
- 敏感文件明确披露传输目的地；
- 云端任务与本地版本节点绑定。

退出条件：非开发者在未安装 CLI、未配置模型 key 的干净机上完成一次真实修改，
并能看懂费用和数据去向。

### M4：团队与企业

对应 P5。

- 私有部署、SSO、组织策略；
- Agent/模型/目录/动作白名单；
- 审计汇聚与导出；
- 集中预算和批量任务；
- 长期支持版本与升级策略。

退出条件：先完成至少两个付费设计伙伴试点，再把私有控制面产品化。

## 6. 未来 90 天执行切片

时间从正式开工日计算，不与自然季度绑定。

| 周期 | 交付 | 验收 |
|---|---|---|
| 0–30 天 | P0 文件关联、右键菜单、拖放；建立格式黄金语料 | 干净机安装/打开/卸载还原；源文件零变化 |
| 31–60 天 | P1 rar/7z；签名发布链；首屏性能与崩溃采集（需同意） | 中文/加密/恶意压缩包测试；发布产物可验证 |
| 61–90 天 | P2 MCP + `workorder.*` 最小版；Claude/Codex 示例 | GUI/CLI/MCP 调同一核心；两个 Agent 端到端 |

版本图先完成数据模型和 Action 契约的设计评审；除非前三项提前达标，不在 90 天内追求完整动画布。

## 7. 质量门槛

### 核心

- 每个安全拒绝都有稳定错误码和测试；
- 所有写动作验证输入/输出不是同一路径；
- 中断后没有半成品冒充成功；
- Action 信封向后兼容，字段只增不静默改义。

### 格式

- 每种格式至少有：正常、损坏、超大、中文路径、恶意样本；
- Rust 权威格式表与 TS viewer 表必须通过 parity 检查；
- 格式声明的能力必须有端到端样本证明。

### GUI

- GUI 只做渲染和宿主能力，不判断业务；
- 重要控件有稳定 automation ID；
- 视觉测试只验证用户能否看到/操作，业务正确性由核心测试证明。

### 发布

提交前保持现有三项全绿：

```bash
cargo test --workspace
node scripts/check-format-parity.mjs
cd apps/redline-desktop && npx tsc --noEmit
```

发布还必须增加：

- 安装/卸载 Windows 沙箱回归；
- 产物签名和 sha256；
- 安装包、便携版和版本清单一致性；
- 至少一台无开发环境、无代理的干净机实测。

## 8. 代码目录演进

```text
crates/
  redline-core/        Action 唯一实现、WorkOrder、Version Graph
  redline-cli/         薄壳
  redline-mcp/         计划：MCP 薄壳
apps/
  redline-desktop/     Tauri 宿主、系统入口和画布
packages/
  redline-core/        Viewer、标注、可复用 UI
services/              不放私有服务端；另建私有仓
docs/
  动作契约.md           对外 Action schema
  决策记录.md           为什么这样做
```

品牌确定后可以改应用显示名和安装包名，但 Rust crate、Action ID 和配置路径应采用兼容迁移，
不能让现有 CLI/MCP 调用因一次营销改名全部失效。
