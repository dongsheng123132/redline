# 影文档协议（ShadowDoc）

> 状态：v1 设计与最小实现，2026-07-31。
>
> 这份文档回答三个问题：要不要发明 AI 时代的新文档格式、预览是不是原件的影子、
> 以及怎样让传统文档在不迁移格式的前提下变得适合 AI。

可执行的 Core 0.1 Working Draft、Schema、合规夹具和首轮数据见
[`spec/shadowdoc/SPEC.md`](../spec/shadowdoc/SPEC.md) 与
[`ShadowDoc Core 0.1 实验报告`](./ShadowDoc实验报告-v0.1.md)。实验结论明确保留反例：
当前真实 Markdown 只有一个全文 unit，上下文缩减为 0%，因此此规范尚不能宣称已经“最佳”。

## 1. 结论：不替代传统格式，建立映射层

不发明一个要求用户放弃 `.docx`、`.pdf`、`.xlsx`、`.pptx` 的新主文件格式。
这些格式已经承载了大量存量文件、打印流程、签章、版式和行业兼容性，新格式冷启动成本极高。

叠象建立的是一个**可丢弃、可重建、与原件哈希绑定的影文档映射层**：

```text
传统原件（权威字节）
   ├── 视觉影子：页面、图层、工作表、缩略图和坐标
   ├── 语义影子：段落、表格、单元格、幻灯片、文本和结构
   ├── 意图层：圈选、文字引用、批注和整体要求
   └── 版本图：哪个 Agent 基于哪个原件生成了哪个新文件
```

影子不是原件，也不冒充无损替代品。删除全部影子后，仍可从原文件重新生成。
真正交付给别人、打印、签章或继续用 Office 打开的，仍是标准文件。

### 1.1 “所有东西都是文档”是产品抽象，不是格式误判

对用户来说，一个任务收到的 `.docx`、PDF、图片、压缩包、文件夹、PSD 或 CAD，
都可以统一叫“文档”：它们都是**需要看懂、标注、加工和交付的任务对象**。

协议内部使用更精确的术语，避免把文件夹或 3D 模型硬说成文字文档：

| 对象 | 含义 |
|---|---|
| `SourceArtifact` | 用户交进来的权威原件；字节和 sha256 不可变 |
| `ArtifactVersion` | 原件或 Agent 生成的一个标准文件版本 |
| `ShadowLayer` | 从一个版本生成的一种视觉、语义、OCR、标注等投影 |
| `ShadowBundle` | 同一个版本下的一组 Shadow Layer |
| `ShadowProject` | 版本节点、影子层、标注、工单和动作历史组成的项目 |

所以“一个源文件可以有多个影子”更准确地说是：

> 一个 `ArtifactVersion` 对应一个 `ShadowBundle`，Bundle 中可以有任意多个可重建的
> `ShadowLayer`；每个新文件版本又拥有自己的 Bundle。

## 2. 它和影核协议是什么关系

不要把两个概念混成一套，也不要让其中一个成为另一个的强制依赖：

| 层 | 回答的问题 | 当前载体 |
|---|---|---|
| **影文档协议 ShadowDoc** | AI 和人看到的“这个文件是什么、哪里是什么” | `document.inspect` / `redline.shadow-document` |
| **影核协议 ActionParity** | AI 和界面能执行哪些稳定动作 | `dispatch(action_id, params)` |
| **版本图 Version Graph** | 哪次动作从哪个原件产生了哪个结果 | 计划中的 `version.*` |

一句话：

> ShadowDoc 描述名词，ActionParity 约束动词，Version Graph 记录历史。

两者是**同源的配套规范**：

- ShadowDoc 可以被解析器、标注工具独立实现，不要求它们采用 ActionParity；
- ActionParity 可以用于任何软件，不要求它处理文档；
- 在叠象里，两者通过 `document.*`、`workorder.*`、`version.*` 等稳定 Action 组合；
- MCP 是调用面，不成为第三份业务逻辑或文档模型。

中文传播可以称“影核体系的影文档规范”；正式开放规范使用中立的
`ShadowDoc Specification / 影文档开放规范`，叠象是参考产品而不是规范所有者。
开源、治理、发布阶段和相邻项目比较见
[ShadowDoc 开源规范与生态计划](./ShadowDoc开源规范与生态计划.md)。

## 3. 原件、视觉影子和语义影子

### 3.1 原件

原件由路径、字节数和 sha256 标识。任何影子、标注和 patch 都绑定原件 sha256；
原件变化后旧映射必须标记陈旧，不能继续静默套用。

### 3.2 视觉影子

视觉影子回答“人在哪里看、圈在哪里”：

- PDF 页；
- Word 连续页面或段落所在区域；
- Excel 工作表与可见单元格区域；
- PPT 幻灯片；
- PSD 图层；
- 压缩包/文件夹树；
- 图片、CAD 和 3D 场景。

视觉影子可以是 canvas、DOM、缩略图或外部转换生成的页面，不要求统一成图片。
它必须报告使用的坐标系和 `unitId`，不能只给一张无法反查来源的截图。

### 3.3 语义影子

语义影子回答“AI 应该读什么、结构是什么”：

- paragraph、heading、table、cell、sheet、slide、page、layer、entry；
- 文字、公式、超链接、注释和必要的样式提示；
- 层级关系；
- `textSha256`，用于发现目标内容漂移；
- 如果解析器能提供，则带源 part、页码、字符范围或 bbox provenance。

第一版不追求把所有格式压成一个完美 AST。格式专有信息可以放在 `meta`，
通用字段只负责寻址、文字、层级和来源。

### 3.4 一个原件可以拥有多个影子层

不同任务需要不同投影，不应该把所有信息塞进一个巨型 JSON：

| Layer | 用途 | 信任类型 |
|---|---|---|
| `visual` | 页面、缩略图、坐标、图层和可见树 | `source-derived` |
| `semantic` | 段落、单元格、幻灯片、条目和结构 | `source-derived` |
| `conversion` | 旧格式转成 PDF/OOXML 后的中间视图 | `source-derived`，但必须标 `lossy` |
| `ocr` | 扫描件文字、bbox 和置信度 | `machine-inferred` |
| `ai-context` | 分块、摘要、实体、向量索引 | `machine-inferred` |
| `annotation` | 圈选、箭头、批注、接受/拒绝 | `human-authored` |
| `diff` | 两个版本之间的视觉和结构变化 | `source-derived` |
| `audit` | 工单、Agent、模型、参数和动作结果 | `system-recorded` |

三类内容不能悄悄混在一起：

1. **原件确定性派生事实**；
2. **OCR/AI 推断**，必须带模型、版本、置信度和生成时间；
3. **人的意图**，必须带作者、锚点和修改时间。

每一层至少记录：

```text
layer id + layer type + source sha256 + content sha256
+ producer id/version + parameters hash + dependencies + trust + lossy
```

相同输入、生产器版本和参数可以命中缓存；任何一项变化都产生新 Layer revision，
不在旧层上原地改写。AI 摘要或 OCR 永远不能冒充原件事实。

## 4. v1 JSON 形状

`document.inspect` 继续是稳定 Action，不另造一个重复的 `document.shadow` 动作。
它的输出增加 ShadowDoc 描述信息：

```jsonc
{
  "shadow": {
    "schema": "redline.shadow-document",
    "schemaVersion": 1,
    "producer": "redline-core/0.1.0",
    "profile": "semantic",
    "granularity": "paragraph",
    "lossy": true,
    "sourceSha256": "f500..."
  },
  "format": "docx",
  "source": {
    "path": "C:\\...\\方案.docx",
    "extension": "docx",
    "bytes": 32435,
    "sha256": "f500..."
  },
  "summary": {},
  "units": [
    {
      "id": "paragraph:1",
      "kind": "paragraph",
      "label": "段落 1",
      "text": "洪山区2026年…",
      "textSha256": "ab12..."
    }
  ]
}
```

`source.sha256` 是原件身份；`shadow.sourceSha256` 是防止影子被脱离原件单独误用的显式绑定。
两者不一致时消费者必须拒绝。

### 4.1 v1 是最小语义层，不是最终 Bundle 形状

当前 `document.inspect` 返回的 `shadow` 是一个最小 `semantic` Layer 描述，
已经足够解决来源哈希、unit 锚点和陈旧拒绝。后续扩展为 Bundle 时保持字段只增不改义：

```jsonc
{
  "shadowProject": {
    "schema": "redline.shadow-project",
    "schemaVersion": 1,
    "projectId": "01J...",
    "rootNodeId": "node:source"
  },
  "artifact": {
    "nodeId": "node:source",
    "contentSha256": "f500...",
    "mediaType": "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
  },
  "shadowBundle": {
    "sourceSha256": "f500...",
    "layers": [
      {
        "id": "layer:semantic:01J...",
        "type": "semantic",
        "trust": "source-derived",
        "contentSha256": "7a21...",
        "producer": "redline-core/0.1.0",
        "lossy": true,
        "dependsOn": []
      },
      {
        "id": "layer:annotation:01J...",
        "type": "annotation",
        "trust": "human-authored",
        "contentSha256": "318c...",
        "producer": "redline-desktop/0.1.0",
        "dependsOn": ["layer:semantic:01J..."]
      }
    ]
  }
}
```

`shadowBundle.sourceSha256` 必须等于当前节点内容哈希。一个 Layer 可以依赖其他 Layer，
但不能形成环；删除缓存层不影响原件、标注意图和版本历史。

### 当前粒度

| 格式 | granularity | 说明 |
|---|---|---|
| docx | `paragraph` | 当前只抽段落文字和摘要，版式并不无损 |
| xlsx | `sheet` | 单元格地址、值和公式铺在 sheet unit 中 |
| pptx | `slide` | 当前是文字大纲，不是高保真幻灯片 |
| pdf | `page` | 按页抽文字；扫描页明确标记需要 OCR |
| text/html | `document` | 单一全文 unit |
| archive | `entry` | 文件清单，不代表已读取每个内部文件 |

所有现有投影都应如实标记 `lossy: true`；即使文本完整，也没有证明全部样式、对象和隐藏内容无损。

## 5. 标注目标：一个位置用多个 Selector

只存 bbox 不够：窗口重排后坐标可能变化；只存段落序号也不够：插入一段后编号会变化。
参考 [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/)，
一条标注可以同时保存多个 Selector：

```jsonc
{
  "sourceSha256": "f500...",
  "selectors": [
    { "type": "UnitSelector", "value": "paragraph:12" },
    { "type": "TextHashSelector", "sha256": "ab12..." },
    { "type": "TextQuoteSelector", "exact": "项目申报表", "prefix": "填写", "suffix": "（盖章）" },
    { "type": "FractionalBoxSelector", "unitId": "paragraph:12", "x": 0.1, "y": 0.2, "width": 0.3, "height": 0.08 }
  ]
}
```

解析顺序：

1. 先确认 `sourceSha256`；
2. 优先使用稳定 `unitId`；
3. 用 `textSha256` 或 quote 验证是否仍指向同一内容；
4. bbox 用于视觉定位，不单独作为语义修改依据；
5. Selector 互相冲突时返回 `stale_annotation`，不猜。

## 6. AI 为什么会更快、更便宜

AI 不应该每次吞下整个原始文件或完整 OCR：

1. 首次打开生成 ShadowDoc 并按源 sha256 缓存；
2. 人的标注先定位到少量 units；
3. 工单只发送选中 units、必要上下文和文档摘要；
4. Agent 需要更多内容时再按 unit 拉取；
5. 输出后只重算受影响的部分和差异。

缓存键必须包含：

```text
source sha256 + parser id + parser version + ShadowDoc schema version + profile
```

任何一项变化都重新生成，避免新版解析器误用旧缓存。

## 7. “好 10 倍”具体指什么

不把 10 倍只理解为渲染帧率。用户真正关心的是：

> **从收到一个文件，到得到一个可验证的新版本，需要多少时间、软件、步骤、token 和风险。**

叠象优先优化五个可测维度：

| 维度 | 传统流程 | 叠象目标 |
|---|---|---|
| 第一次打开 | 找软件、安装、登录、转换 | 常见小文件冷开 P50 <1 秒，P95 <3 秒 |
| 指出修改 | 截图、描述“第二页右边” | unit + quote + bbox 精确工单 |
| AI 上下文成本 | 上传全文、重复解析 | 默认只发送相关 units，记录节省比例 |
| 结果确认 | 人工来回切窗口 | 左右同位置对照 + 结构化 diff |
| 风险 | 覆盖、版本散落、无法追责 | 原件不变、每次动作生成不可变节点 |

“10 倍”是否成立由实际任务实验判断：

- 同一份 50 页 PDF/合同，用传统聊天和叠象各完成一次修改；
- 记录从打开到确认的总分钟数、交互轮数、发送 token、错误修改数；
- 只有至少一个核心指标稳定提升 5–10 倍，且其他指标没有显著恶化，才对外宣传。

## 8. 格式策略：少数深做，多数能开

### 深度优化的七类

1. PDF；
2. DOCX；
3. XLSX/CSV；
4. PPTX；
5. 图片与扫描件；
6. 压缩包与文件夹；
7. 文本、Markdown、HTML、JSON/XML。

这七类需要打通：

```text
快速首屏 → 搜索/定位 → ShadowDoc → 标注 → Agent → 新文件 → diff
```

### 传统格式适配层

`.doc/.xls/.ppt/.rtf/.odt/.ods/.odp` 等格式不直接伪装成现代格式解析。
计划通过进程外适配器转换到 PDF/OOXML/HTML，再明确标记为“转换预览”：

```text
原件（永不改）
  → 外部适配器（LibreOffice/Pandoc/专用工具）
  → 临时标准格式
  → 视觉 + 语义影子
  → 标注和 AI
  → 新的标准输出文件
```

转换预览必须记录适配器、版本、命令、输出哈希和丢失风险。转换失败仍保留原件，
不能用乱码或空白页冒充支持。

### 广度适配器

可借鉴但不直接绑定单一实现：

- [DoclingDocument](https://docling-project.github.io/docling/concepts/docling_document/)：
  层级、bbox 和 provenance；
- [Pandoc AST](https://pandoc.org/filters.html)：文本结构 reader/AST/writer；
- [Microsoft MarkItDown](https://github.com/microsoft/markitdown)：面向 LLM 的 token 友好 Markdown；
- [Apache Tika formats](https://tika.apache.org/3.0.0/formats.html)：广泛的格式探测与文本/元数据抽取。

这些工具都应作为可替换的进程外 `ParserAdapter`，核心协议不依赖其内部类型。

## 9. 预览性能路线

### PDF

- PDF.js worker 常驻复用；
- 先出第一页和缩略图，再懒加载其他页；
- 页面虚拟化，只保留视口附近 canvas；
- 文本层/OCR 分页缓存；
- 标注锚到 `page:N`，不重新解析全文。

### DOCX

- 核心一次解析出段落、表格和标题；
- 视觉层渐进渲染，先正文后图片；
- 语义 units 与 DOM 节点绑定，不再使用一个 `document:1` 覆盖全文；
- 大图延迟解码，重复打开命中 sha256 缓存。

### XLSX

- 工作表列表先出，单个 sheet 按需解码；
- 视口虚拟化，不再固定截断 500 行；
- 单元格地址成为稳定 selector；
- 公式、显示值和原始值分开保存。

### PPTX

- 第一阶段用外部转换生成逐页视觉影子，同时保留核心文字大纲；
- 第二阶段把 shape、文字和图片映射到 slide unit；
- 不再把“只有大纲”宣传成高保真预览。

## 10. 无限画布移动的是版本节点，不是被反复覆盖的影子

用户看到的是向右生长、可以随时向上或向下分叉的无限画布；底层记录的是不可变版本图：

```text
原件节点 A
  └─ ShadowBundle A（visual / semantic / OCR / annotation）
       └─ WorkOrder 1 + Agent X
            └─ 新文件节点 B
                 ├─ ShadowBundle B
                 ├─ WorkOrder 2 + Agent X ─→ 新文件节点 C
                 └─ WorkOrder 3 + Agent Y ─→ 新文件节点 D
```

交互规则：

1. 打开原件 A，只读生成或复用它的多个影子层；
2. 人在视觉层圈点，标注同时锚到语义 unit、文字哈希和坐标；
3. WorkOrder 固定引用的节点、Layer revision、Selectors、指令、权限和输出路径；
4. Agent 读取工单允许的原件/影子层，输出一个**新标准文件**；
5. 核心验证新文件后创建节点 B，并为 B 异步生成新的 ShadowBundle；
6. 用户满意就继续从 B 向右，不满意可以从 A 或 B 换 Agent 分叉；
7. 画布平移、缩放和卡片位置只是 UI 状态；节点、边和哈希才是业务事实。

AI 可以提交结构化 patch，但 patch 必须由格式适配器应用到**新副本**并验证。
AI 不能直接把 ShadowDoc 改一改就冒充最终 `.docx`/PDF，也不能覆盖原件。

这个模型让“无限修改”仍然可审计：每次修改知道基于哪个版本、看了哪些层、
用了什么 Agent、产生了哪个文件；切换 Agent 不需要重新上传和重新理解整个原件。

## 11. `.shadowdoc` 是可选项目容器，不是新的 Office 格式

未来可以提供一个便携的 `项目名.shadowdoc`，用于保存整个工作台：

- manifest、项目 ID 和 schema 版本；
- 原件引用或可选的内嵌原件，以及每个内容哈希；
- ShadowBundle/Layer manifest 和可丢弃缓存；
- 人工标注、WorkOrder、版本节点和 ActionEdge；
- Agent/模型/适配器的审计信息；
- 画布布局等非业务 UI 状态。

它是 sidecar/project container，不要求收件人以后都用它办公。导出和交付仍是 PDF、
DOCX、XLSX 等标准文件。打开容器时不能自动执行其中的 Agent 命令；外部路径、压缩条目、
脚本内容和网络引用都按不可信输入处理。

容器可以采用“目录 + manifest”先验证模型，规模和跨设备需求成立后再决定是否封装为
ZIP/SQLite。不要先发明复杂二进制格式，再寻找使用场景。

## 12. 实现阶段

### v1：身份和锚点

- `document.inspect` 输出 ShadowDoc schema；
- unit 增加 `kind` 和 `textSha256`；
- 修正 Rust 与 PDF/XLSX/PPTX viewer 的 unit ID 漂移；
- Tauri 宿主让预览直接消费核心 Snapshot，viewer 只补视觉尺寸。

### v2：多 Selector 标注

- 标注保存 source sha256、unit、text quote/hash 和 bbox；
- 导出 `workorder.*`；
- stale annotation 明确拒绝。

### v3：缓存与按需上下文

- 内容寻址缓存；
- 分页/分 sheet OCR 与解析；
- 工单按 unit 拉取，记录 token 节省。

### v4：外部格式适配器

- LibreOffice/Pandoc/Tika/Docling 等进程外适配协议；
- 旧 Office 与 ODF 转换预览；
- 适配器版本、许可证、超时和安全沙箱。

## 13. 名称边界

`ShadowDoc` 准确、好记，也与“原件不动、建立影子层”的技术方向高度一致；
但它更适合做**协议名/项目容器名**，产品品牌仍使用“叠象 / Stelora”等独立名称。

公开使用建议带命名空间：

- `Stelora ShadowDoc`：面向产品和开发者；
- `Redline ShadowDoc`：代码尚未完成品牌迁移期间；
- `redline.shadow-document`：现有机器 schema，v1 不因营销命名而破坏兼容。

公开检索已经存在[同名旧文档项目](https://app.readthedocs.org/projects/shadowdoc/)、
[同名医疗服务项目](https://www.newswise.com/articles/venturelab-founders-building-startups-in-an-uncertain-world)，
公开网络流传的 [Google Drive 内部 API 快照](https://gist.github.com/chocolatkey/53ac6b80bc69a256543903f001e01e68)
也出现过这个术语。因此裸用 `ShadowDoc` 不能视为商标或品牌可用性结论。
正式发布前仍需做中国及目标市场的商标、公司名、域名和应用商店检索；
技术协议名与商业品牌分离能降低未来迁移成本。

## 14. 非目标

- ShadowDoc 不取代 Office/PDF 标准；
- 不承诺从通用 AST 无损写回所有格式；
- 不让 AI 直接修改 ShadowDoc 后冒充原文件；
- 不把截图 OCR 当作唯一事实源；
- 不为追求格式数量而把乱码、大纲或元数据宣传成高保真预览；
- 不把解析器缓存当原件，缓存随时可以删除重建。
